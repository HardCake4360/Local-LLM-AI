# LLM 채팅 API 서버 프로젝트 분석 문서

## 1. 프로젝트 개요

이 프로젝트는 Flask 기반의 경량 API 서버로, 로컬 Ollama LLM과 FAISS 기반 검색을 결합해 채팅 응답을 생성한다. 단순 질의응답 서버가 아니라 다음 요소를 함께 포함한 구조다.

- 대화 로그 저장
- 대화 요약 캐시 생성
- 세계관/문서 기반 RAG 검색
- 페르소나 기반 답변 스타일 제어
- 스트리밍 응답 제공

즉, 성격상 "로컬 LLM + RAG + 캐릭터 페르소나 + 메모리 요약"을 결합한 실험형 채팅 API 서버에 가깝다.

## 2. 디렉터리 구조

핵심 구조는 다음과 같다.

```text
app/
  server.py              # Flask API 서버 진입점
  llmClient.py           # Ollama 호출, 프롬프트 생성
  retriever.py           # SentenceTransformer + FAISS 검색
  chatlog.py             # 대화 로그/요약 캐시 저장
  summarizer.py          # 규칙 기반 요약
  summarizer_llm.py      # LLM 기반 요약
  persona_store.py       # 페르소나 JSON 로드
  documentHandler.py     # PDF 텍스트 추출/청크 분할
  dependencies.txt       # 의존성 메모
  data/
    personas/            # 페르소나 정의 JSON
    world/               # 검색 대상 세계관 텍스트
    index/               # FAISS 인덱스와 청크 pickle
    chatlogs/            # 사용자별 대화 로그/요약
    pdfs/                # 원본 PDF 자료

ui/
  app.py                 # Streamlit 클라이언트
```

## 3. 핵심 동작 방식

### 3.1 서버 시작

`app/server.py`가 메인 엔트리 포인트다.

- Flask 앱과 CORS를 초기화한다.
- `Retriever()`를 전역으로 생성한다.
- 시작 시 `init_index()`를 통해 세계관 문서를 인덱싱하거나 기존 인덱스를 로드한다.
- 배포 실행은 Flask 개발 서버가 아니라 `waitress.serve(..., port=5000)`를 사용한다.

### 3.2 채팅 요청 처리 흐름

주요 엔드포인트는 `POST /ask-stream`이다. 요청 처리 순서는 다음과 같다.

1. `question`, `user_id`, `personaKey`를 JSON에서 읽는다.
2. 사용자 발화를 JSONL 로그에 즉시 저장한다.
3. `retriever.search(question)`로 관련 텍스트 청크를 검색한다.
4. `personaKey`가 있으면 페르소나 JSON을 로드한다.
5. 사용자 요약 캐시가 있으면 검색 청크 앞에 `[대화요약] ...` 형식으로 추가한다.
6. `build_prompt_v2()`로 최종 프롬프트를 구성한다.
7. `query_ollama_stream()`으로 Ollama의 `/api/generate` 스트리밍 응답을 받아 클라이언트에 그대로 흘려보낸다.
8. 스트리밍이 끝나면 완성된 답변을 다시 로그에 저장한다.
9. 백그라운드 스레드에서 최신 로그를 요약하고 summary 캐시를 갱신한다.

이 구조 덕분에 응답 지연을 줄이면서도, 다음 요청부터는 요약 메모리를 프롬프트에 재사용할 수 있다.

## 4. API 엔드포인트 정리

현재 확인되는 엔드포인트는 아래와 같다.

- `GET /log/summary`
  - 사용자 로그를 읽고 규칙 기반 요약 결과를 반환
- `GET /log/summary-llm`
  - 사용자 로그를 읽고 LLM 기반 요약 결과를 반환
- `POST /log/reset`
  - 대화 로그와 요약 캐시를 초기화
- `POST /ask-stream`
  - 스트리밍 방식으로 LLM 응답을 반환

주의할 점은 서버에 일반 JSON 응답용 `/ask` 엔드포인트는 없는데, `ui/app.py`는 `http://localhost:5000/ask`를 호출하고 있다는 점이다. 현재 코드 그대로라면 UI는 정상 동작하지 않을 가능성이 높다.

## 5. 모듈별 역할 분석

### 5.1 `server.py`

전체 오케스트레이션 역할을 맡는다.

- API 라우팅
- 검색기 초기화
- 로그 저장
- 프롬프트 생성 호출
- 스트리밍 응답 처리
- 백그라운드 요약 갱신

실질적으로 프로젝트의 중심 모듈이다.

### 5.2 `llmClient.py`

LLM 관련 기능을 담당한다.

- `build_prompt()`: 기본 RAG 프롬프트
- `build_prompt_v2()`: 페르소나 정보를 포함한 개선형 프롬프트
- `query_ollama()`: 단건 응답
- `query_ollama_stream()`: 스트리밍 응답

특징:

- Ollama를 직접 HTTP로 호출한다.
- 기본 호스트는 `http://localhost:11434`
- 모델명은 호출부에서 주입하며, 현재 서버는 주로 `gemma3:12b`를 사용한다.

### 5.3 `retriever.py`

검색 파이프라인을 담당한다.

- `SentenceTransformer('all-MiniLM-L6-v2')`로 문서 임베딩 생성
- `faiss.IndexFlatL2`로 벡터 인덱스 구성
- 질문 임베딩 후 상위 청크 검색
- 인덱스/청크 저장 및 재로딩

현재는 단일 정적 인덱스만 사용하며, 검색 결과를 거리 기준으로 정렬해 상위 3개 청크를 반환한다.

### 5.4 `chatlog.py`

대화 메모리 저장소 역할을 한다.

- 사용자별 `*.jsonl` 로그 파일 저장
- 최근 N개 로그 읽기
- 요약 캐시 `*.summary.json` 저장/로드/삭제

DB 없이 파일 기반으로 동작하므로 구조는 단순하지만, 동시성이나 검색성 측면에서는 한계가 있다.

### 5.5 `summarizer.py`

규칙 기반 요약기다.

- 최근 대화 일부를 붙여 간단한 요약 생성
- 토큰 빈도 기반 키프레이즈 추출
- 특정 단어 유무로 신뢰도와 친밀도 추정

품질은 제한적이지만, LLM 요약 실패 시 fallback으로 쓰기 적합하다.

### 5.6 `summarizer_llm.py`

LLM에게 요약을 맡기는 모듈이다.

- JSON 스키마를 강하게 요구하는 프롬프트 사용
- 응답 JSON 파싱 실패 시 규칙 기반 요약으로 fallback 가능
- `summary`, `user_emotion`, `user_goal`, `relationship_state`, `topics` 등을 구조화해서 저장

이 모듈 덕분에 단순 요약이 아니라 "대화 메모리 객체"를 생성하는 구조가 된다.

### 5.7 `persona_store.py`

페르소나 JSON을 로드하는 단순 저장소다.

- `list_persona_keys()`
- `load_persona(key)`
- `lru_cache` 적용

현재는 파일 기반 정적 로딩 구조다.

### 5.8 `documentHandler.py`

PDF 텍스트 추출 및 분할 기능을 제공한다.

- PyMuPDF 기반 텍스트 추출
- 문자 수 기반 청크 분할

다만 현재 `server.py` 안에서는 import만 되어 있고 실제 런타임에서 거의 사용되지 않는다. 현재 서버의 실제 인덱싱은 PDF가 아니라 `app/data/world/*.txt` 기반이다.

## 6. 데이터 흐름 관점에서 본 구조

이 프로젝트의 데이터 흐름은 아래처럼 요약할 수 있다.

```text
사용자 질문
  -> 로그 저장
  -> 벡터 검색
  -> 요약 캐시 로드
  -> 페르소나 로드
  -> 프롬프트 조합
  -> Ollama 스트리밍 호출
  -> 응답 스트리밍 반환
  -> 응답 로그 저장
  -> 백그라운드 요약 갱신
```

구조적으로는 "검색 메모리"와 "대화 메모리"를 동시에 프롬프트에 주입하는 형태다.

- 검색 메모리: `world` 텍스트에서 가져온 RAG 청크
- 대화 메모리: 이전 대화의 요약 캐시
- 성격 메모리: persona JSON

## 7. 현재 구현의 강점

### 7.1 구조가 단순하고 이해하기 쉽다

Flask + 파일 저장 + Ollama HTTP 호출 조합이라 전체 구조를 빠르게 파악할 수 있다.

### 7.2 실험 속도가 빠르다

- DB가 없다
- 외부 SaaS 의존성이 거의 없다
- 모델은 로컬 Ollama로 바로 교체 가능하다

프로토타입이나 연구용으로 매우 빠르게 반복 실험하기 좋은 형태다.

### 7.3 페르소나와 메모리 개념이 이미 들어가 있다

단순 RAG 챗봇이 아니라 캐릭터성 유지와 대화 문맥 유지까지 시도하고 있다는 점이 이 프로젝트의 가장 큰 특징이다.

### 7.4 스트리밍 응답을 지원한다

`/ask-stream`이 있어 실제 채팅 UX에 유리하다.

## 8. 확인된 문제점과 리스크

### 8.1 UI와 서버 엔드포인트가 맞지 않는다

`ui/app.py`는 `/ask`를 호출하지만 서버는 `/ask-stream`만 제공한다. 현재 상태 그대로라면 Streamlit UI는 실패할 가능성이 높다.

### 8.2 경로가 실행 위치에 강하게 의존한다

예를 들어 `server.py`와 `chatlog.py`는 다음처럼 상대경로를 하드코딩하고 있다.

- `virtualEnv/RAG_model/app/data/...`

현재 워크스페이스 루트가 이미 `virtualEnv/RAG_model`이기 때문에, 여기서 실행하면 경로가 중복되어 깨질 수 있다. 이 프로젝트는 "어디서 실행하느냐"에 따라 동작 여부가 달라질 가능성이 있다.

권장 방식은 `__file__` 기준 절대경로 조합이다.

### 8.3 예외 처리와 운영 로그가 제한적이다

- 로그는 대부분 `print()` 기반이다.
- 구조화 로그가 없다.
- 백그라운드 스레드 실패 시 재시도/관측성이 약하다.

개발 단계에서는 충분하지만, 서버 운영 단계에서는 추적이 어렵다.

### 8.4 파일 기반 저장소의 동시성 이슈 가능성

대화 로그와 요약 파일을 단순 append/write 방식으로 다루고 있어, 다중 요청 환경에서는 충돌 가능성이 있다.

### 8.5 모델/검색 설정이 하드코딩되어 있다

예:

- 모델명 `gemma3:12b`
- 검색 개수 `top_k=3`
- 포트 `5000`
- Ollama 호스트 `localhost:11434`

환경변수나 설정 파일로 분리되지 않아 운영 유연성이 낮다.

### 8.6 사용되지 않는 코드와 설정이 남아 있다

- `PDF_NAME`, `PDF_PATH`
- `documentHandler` 관련 import
- `build_prompt()`는 현재 주 흐름에서 사용되지 않음

실험 과정의 흔적이 남아 있어 유지보수 시 혼란을 줄 수 있다.

### 8.7 요약 후처리 품질 이슈 가능성

`query_ollama()`는 응답 뒤에 `<END>` 마커를 붙이는 후처리를 한다. 이 값이 `summarizer_llm.py`의 JSON 파싱 흐름과 섞일 경우, 모델 응답 형식에 따라 불안정성이 생길 수 있다. 현재는 정규식과 fallback으로 어느 정도 버티지만 구조적으로는 분리하는 편이 안전하다.

## 9. 실행 및 의존성

의존성 메모 기준 주요 런타임 구성은 다음과 같다.

- Python 3.10+
- Flask
- Flask-CORS
- Waitress
- requests
- sentence-transformers
- faiss-cpu
- numpy
- pymupdf
- streamlit (선택)
- Ollama 서버

즉, 이 프로젝트는 파이썬 서버 자체만으로 완결되지 않고, 별도로 로컬 Ollama 모델이 준비되어 있어야 정상 동작한다.

## 10. 개선 우선순위 제안

우선순위를 나누면 다음과 같다.

### 1순위: 바로 수정해야 하는 항목

- UI와 API 엔드포인트 일치시키기
- 파일 경로를 `Path(__file__)` 기준으로 정리하기
- 설정값을 환경변수 또는 config 파일로 분리하기

### 2순위: 안정화 항목

- 파일 저장 대신 SQLite 같은 경량 DB로 로그/요약 관리
- 로깅 체계 표준화
- 백그라운드 요약 실패 처리 강화

### 3순위: 기능 고도화

- 사용자별/페르소나별 세션 관리 개선
- RAG 대상 문서 동적 업로드
- 검색 청크 재랭킹
- 프롬프트 템플릿 분리
- 요약 메모리와 장기 메모리의 분리

## 11. 종합 평가

이 프로젝트는 "로컬에서 돌아가는 캐릭터형 RAG 채팅 서버"라는 방향이 명확하다. 특히 아래 3가지가 잘 결합되어 있다.

- 문서 검색 기반 응답
- 페르소나 기반 스타일 제어
- 대화 요약 기반 메모리 유지

반면 현재 상태는 연구/프로토타입 단계에 더 가깝고, 실행 경로 의존성, UI/API 불일치, 파일 저장 기반 구조 같은 운영 리스크가 존재한다.

따라서 이 프로젝트는 다음처럼 평가할 수 있다.

- 아이디어와 구조 방향성: 좋음
- 실험/데모 적합성: 높음
- 운영 안정성: 보완 필요
- 유지보수성: 중간

## 12. 한 줄 요약

이 프로젝트는 Ollama, FAISS, 페르소나, 대화 요약 메모리를 결합한 Flask 기반 LLM 채팅 API 서버이며, 프로토타입으로는 충분히 흥미롭고 기능적으로도 의미가 있지만, 실제 서비스화 전에는 경로/설정/엔드포인트/저장소 구조를 정리하는 작업이 먼저 필요하다.
